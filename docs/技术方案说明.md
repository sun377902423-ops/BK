# BKSYS-MED 远程医疗会诊系统 — 技术方案说明

---

## 一、系统概述

BKSYS-MED 是一套部署在用户本地服务器的跨国远程医疗影像会诊系统。系统以**医学影像查看**和**实时视频会诊**为核心，整合患者管理、结构化报告、体征数据记录等功能，实现从影像采集、远程诊断到报告签署的完整工作闭环。

| 项目 | 内容 |
|------|------|
| 目标用户 | 布基纳法索等非洲法语区基层医院 ↔ 中国三甲医院专家 |
| 网络环境 | Starlink 卫星互联网 / 光纤宽带 + 本地服务器部署 |
| 部署方式 | 全部软件部署在用户自有服务器上，数据不经过第三方 |
| 访问方式 | 电脑/手机浏览器直接访问，无需安装客户端 |
| 移动端支持 | Android 手机和平板可安装 APK，随时随地参与会诊和阅片 |

## 三、通量与并发能力

### 3.1 设计容量

| 并发场景 | 设计容量 | 说明 |
|---------|---------|------|
| 同时进行的视频会诊 | 5 — 8 场 | 每场 2-5 人参与 |
| 同时在线的阅片用户 | 20 人 | 每人查看不同检查 |
| 同时使用系统的总人数 | 约 40 — 60 人 | 含会诊参与 + 阅片 + 其他操作 |
| 每日处理检查量 | 50 — 100 例 | CT/MR 检查 |

### 3.2 带宽需求分解

#### 视频通话带宽（最大消耗项）

| 会诊场次 | 每路视频 | 总上行 | 总下行 |
|---------|---------|-------|-------|
| 5 场同时（每场 4 人） | 1.5-3 Mbps（720p） | 15 Mbps | 45 Mbps |
| 8 场同时（每场 4 人） | 1.5-3 Mbps（720p） | 24 Mbps | 72 Mbps |

> 视频通话采用转发架构，每个客户端只发送 1 路上行流，服务端转发给其他参与者。上行压力小，下行压力随观看人数增加。

#### 影像浏览带宽

| 操作场景 | 瞬时峰值 | 平均带宽 |
|---------|---------|---------|
| 20 人同时阅片（首次加载 CT） | ~200 Mbps（短时爆发） | 30-50 Mbps（正常操作） |
| 查看已缓存的影像 | 较低 | < 10 Mbps |

> 每例 CT 检查约 200-500 张图像，首次加载约 100-300 MB。系统会自动缓存已加载的影像，重复查看无需重新下载。

#### 日常 API 操作

| 操作类型 | 频率 | 带宽占用 |
|---------|------|---------|
| 会诊详情轮询 | 每 5 秒/人 | 极低 |
| 通知检查 | 每 15 秒/人 | 极低 |
| 报告/患者/会诊 CRUD | 随操作触发 | 极低 |

#### 总带宽建议

| 负载等级 | 适用场景 | 建议带宽 |
|---------|---------|---------|
| 标准 | 5 场会诊 + 10 人阅片 | **200 Mbps** |
| 高负载 | 8 场会诊 + 20 人阅片 | **500 Mbps** |

> **关键结论**：视频通话是带宽瓶颈。200 Mbps 可流畅支持 5 场会诊 + 10 人阅片；若要支持 8 场 + 20 人同时使用，需 500 Mbps。

### 3.3 服务器资源消耗

| 资源 | 消耗说明 | 建议配置 |
|------|---------|---------|
| **CPU** | LiveKit 视频转发为主，数据库查询为辅 | 8 核及以上 |
| **内存** | PostgreSQL + Redis + 系统服务 + 文件缓存 | 32 GB |
| **系统盘** | 操作系统 + Docker 镜像 + 程序代码 | 240 GB SSD |
| **数据盘** | 近期影像数据（医生高频访问） | **4 TB SSD**（关键：阅片速度取决于此处）|
| **长期存储** | NAS 机械硬盘归档 | 8 TB（RAID 1，约 5-8 年容量）|

### 3.4 并发连接数参考

| 连接类型 | 数量 | 说明 |
|---------|------|------|
| HTTP 长连接（前端→后端） | ~60 | 每个在线用户 1 个长连接 |
| WebSocket（会诊聊天） | ~40 | 按会诊参与人数 |
| WebRTC（视频通话） | ~40 | 每路视频 1 个连接 |
| DICOM 接收 | 1-3 | CT/MR 设备上传 |

> 以上连接数对服务器压力很小，瓶颈不在连接数而在带宽。

## 五、网络与接入

### 5.1 互联网接入要求

| 项目 | 要求 |
|------|------|
| 宽带类型 | 企业宽带（上下行对称） |
| 建议带宽 | 100-500 Mbps |
| 公网 IP | 需要 1 个固定公网 IP |
| IP 获取方式 | 向电信/联通等运营商申请 |

> 家用宽带上行通常仅 30-50 Mbps，无法满足多场会诊同时进行的视频上传需求。必须使用企业宽带。

### 5.2 防火墙端口映射

需要在路由器上做端口映射，将外网请求转发至主服务器内网 IP：

| 端口 | 协议 | 用途 | 必要性 |
|------|------|------|--------|
| 80 | TCP | HTTP 访问（自动跳转到 HTTPS） | 必需 |
| 443 | TCP | HTTPS 加密访问 | **必需** |
| 4242 | TCP | 接收 CT/MR 影像数据 | 必需（影像传输） |
| 7880 | TCP | 视频通话 HTTP 信令 | 必需（会诊） |
| 7881 | TCP | 视频通话 TCP 备用通道 | 必需（会诊） |
| 7882 | UDP | 视频通话主通道 | **必需（会诊核心端口）** |
| 50000-50100 | UDP | 视频通话媒体数据端口池 | **必需** |

> 端口 7880-7882 和 50000-50100 是 LiveKit 视频通话服务必须开放的端口，缺失会导致视频无法连接。

## 七、核心业务流程说明

### 7.1 影像从检查到归档全流程

```
① CT/MR 设备完成扫描
       │
② 设备通过 DICOM 协议自动推送影像（端口 4242）
       │
③ Orthanc 接收影像并存储到 SSD 数据盘
       │
④ 系统后台自动同步，检查出现在业务列表中
       │
⑤ 医生在电脑或手机上查看影像（OHIF Viewer）
       │
⑥ 可以发起远程会诊，双方同步阅片讨论
       │
⑦ 会诊结束，医生撰写诊断报告（可附加体征数据）
       │
⑧ 报告签署确认后，影像数据从 SSD 迁移至 NAS 长期归档
```

### 7.2 远程会诊流程

```
① 本地医生创建会诊（选定患者 → 关联检查 → 填写病情描述）
       │
② 从系统中选择要邀请的远程专家（可指定多人）
       │
③ 系统通知被邀请人（铃铛角标 + 提示音）
       │
④ 专家接受邀请，进入会诊室
       │
⑤ 发起人点击"开始会诊"，所有人进入视频会议室
       │
⑥ 会诊中可做：
   ┌────────────────────────────────────┐
   │ • 实时视频通话（多方）              │
   │ • 文字聊天                          │
   │ • 同步查看影像（分屏或全屏）         │
   │ • 记录患者体征数据（血压/心率等）      │
   └────────────────────────────────────┘
       │
⑦ 会诊结束后，流程自动进入报告撰写阶段
```

## 九、安全保障体系

| 安全层级 | 措施 | 说明 |
|---------|------|------|
| **传输安全** | HTTPS 加密 | 所有网页和 API 请求均加密传输 |
| **身份认证** | JWT 令牌 | 登录后签发令牌，12 小时过期 |
| **权限控制** | RBAC 模型 | 4 角色 38 权限，按钮级控制 |
| **防越权** | 后端中间件检验 | 每次 API 请求校验用户权限 |
| **防误操作** | 确认对话框 | 删除/签署等关键操作需二次确认 |
| **容错保护** | ErrorBoundary | 页面异常时显示错误提示，不会白屏 |
| **数据备份** | 自动备份 | 数据库定时备份到 NAS |
| **断电保护** | UPS | 意外断电时可正常关机，防止数据损坏 |
